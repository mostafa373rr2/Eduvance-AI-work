# Backend development

## Reproduce the validated Windows environment

The acceptance baseline was tested on Windows x64 with Python 3.13.5. From a
fresh checkout, using an installed Python 3.13 interpreter:

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r Backend/requirements.txt -c Backend/constraints-windows-py313.txt
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m pytest Backend/tests -q -p no:cacheprovider -rs
.\.venv\Scripts\python.exe Backend/scripts/verify_sqlite_setup.py
```

The constraints file pins the 58 resolved distributions tested on this platform;
it is a version snapshot, not a package-hash lock or a guarantee for other Python
versions/operating systems. `requirements.txt` retains the direct dependency ranges.
Install with both files for the tested baseline. When updating dependencies,
resolve in a separate environment, test, and refresh constraints deliberately.

The setup-check script uses a disposable database below the workspace, tests
Alembic CLI upgrade/check/downgrade/re-upgrade, and removes that database afterwards.
It does not migrate or roll back the configured application database. On this host,
the suite skips symlink creation without the required Windows privilege and emits
a Starlette/httpx TestClient deprecation warning; these are recorded limitations.

## Run the backend

Run from the repository root using the project virtual environment. If no `.env`
exists, copy `Backend/.env.example` to `.env` and set the `EDUVANCE_` variables.
Initialize a fresh database using the [database setup guide](../Database/README.md).

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn Backend.main:app --host 127.0.0.1 --port 8000
```

Interactive API documentation: `http://127.0.0.1:8000/docs`.

| Endpoint | Success | Failure |
|---|---|---|
| `GET /health/live` | 200, `{"status":"alive"}` | Independent of database readiness |
| `GET /health/ready` | 200, `{"status":"ready"}` | 503, `{"status":"not_ready"}` |

The application can start before database initialization. It does not run
migrations or create tables on startup. Readiness verifies Alembic heads and
executes zero-row queries against mapped tables to detect missing tables/columns.
It does not validate every constraint, write permission, or other learning service.
Run `alembic check` for schema comparison. Health errors do not expose database
connection details. Driver connection timeouts still control how long an
unreachable database may take to report failure.

These health routes are outside `/api/v1`. Readiness checks only the database;
authentication also requires the signing-key setup below. Course containers are
available; content generation and learner features are not implemented yet.
The application disposes its default engine pool on shutdown.
Tests may pass their own engine to `create_app`; callers own its cleanup.

```powershell
.\.venv\Scripts\python.exe -m pytest Backend/tests/test_app.py Backend/tests/test_migrations.py Backend/tests/test_config.py -q -p no:cacheprovider
```

Tests use disposable in-memory SQLite databases, including startup, migration
readiness, failure reporting, and recovery. PostgreSQL remains unvalidated.

## Accounts

Install the updated `Backend/requirements.txt`. Generate a signing key locally:

```powershell
.\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(48))"
```

Set the generated value as `EDUVANCE_SECRET_KEY` in your ignored root `.env`.
An empty key, a key shorter than 32 UTF-8 bytes, or the old development placeholder
disables all account endpoints with HTTP 503. Only HS256 and a positive
`EDUVANCE_ACCESS_TOKEN_EXPIRE_MINUTES` are supported. Restart after configuration
changes. No actual key is included in source or generated by the application.

| Endpoint | JSON request / authorization | Success |
|---|---|---|
| `POST /api/v1/auth/register` | `email`, `password`, `full_name` | 201: public user fields |
| `POST /api/v1/auth/login` | `email`, `password` | 200: `access_token`, `token_type`, `expires_in` (seconds) |
| `GET /api/v1/auth/me` | `Authorization: Bearer <access_token>` | 200: current public user fields |

Emails are validated and lowercased for registration and login. Passwords require
at least 12 characters and at most 72 UTF-8 bytes; they are never trimmed or
truncated. Names must be nonblank and at most 150 characters. Extra request fields
are rejected, and registrations always receive the LEARNER role. Duplicate emails
return 409; invalid input returns 422; invalid login or bearer credentials return
401. Public user responses exclude password hashes.

Passwords use salted bcrypt hashes. Tokens contain a user ID, issuer, audience,
access-token type, issue time and expiration. `/me` checks the account still exists.
Login and `/me` responses disable caching. No refresh tokens, logout revocation,
email verification, password reset or rate limiting are implemented in this step.
Course ownership enforcement is described below.

```powershell
.\.venv\Scripts\python.exe -m pytest Backend/tests/test_auth.py Backend/tests/test_app.py Backend/tests/test_config.py Backend/tests/test_migrations.py -q -p no:cacheprovider
```

## Course containers and ownership

All course endpoints require `Authorization: Bearer <access_token>`.

| Endpoint | Request | Success |
|---|---|---|
| `POST /api/v1/courses` | JSON `title`, `domain`, optional `description` | 201: newly created DRAFT course |
| `GET /api/v1/courses` | Optional `limit` (1–100, default 20), `offset` (0 or greater) | 200: array of the current user's courses |
| `GET /api/v1/courses/{course_id}` | Course UUID | 200: owned course |

Responses include `id`, `title`, `domain`, `description`, `status`, `created_at`,
and `updated_at`. Successful responses use `Cache-Control: no-store`.
Lists are ordered by descending creation time, then ID for ties.

Title and domain are trimmed and must be nonblank, with limits of 255 and 100
characters respectively. Description accepts null or up to 10,000 characters.
Ownership comes exclusively from the authenticated user; client-supplied `user_id`,
`id`, `status`, or other extra fields are rejected with 422. An absent or foreign
course ID returns the same 404 response. Invalid UUIDs/pagination return 422;
missing or invalid credentials return 401.

These endpoints create course containers only. They do not upload, extract or
generate learning material. Updates, deletion and sharing are not implemented.
Storage paths alone do not authorize file access; protected document/asset
delivery must reuse the ownership check before accessing files. The source-document
download endpoint below now applies that check; generated-asset delivery is pending.

```powershell
.\.venv\Scripts\python.exe -m pytest Backend/tests/test_courses.py Backend/tests/test_auth.py Backend/tests/test_app.py Backend/tests/test_config.py Backend/tests/test_migrations.py -q -p no:cacheprovider
```

## Source-document downloads

`GET /api/v1/courses/{course_id}/documents` lists source-document metadata for
the authenticated course owner. It returns an array with `id`, `course_id`,
`filename` (basename only), `page_count`, `file_size_bytes`, `upload_status`,
`created_at`, and `download_url`. Filesystem paths and internal hashes are omitted.
Download URLs are same-origin paths and require the same bearer authentication.
They follow the configured API prefix.

The list accepts `limit` (1–100, default 20) and `offset` (0 or greater), ordered
by ascending creation time then ID. Empty owned courses return `[]`. Foreign and
unknown courses return the same 404; missing/invalid tokens return 401. Success
uses `Cache-Control: private, no-store`. Listing reads metadata only, so a record
can be listed even if its file is missing; the download request then returns 404.

`GET /api/v1/courses/{course_id}/documents/{document_id}/download` requires a
bearer token. The course must belong to the authenticated user, and the Document
record must belong to that course. These checks happen before file lookup.

Success returns PDF bytes as an attachment named `{document_id}.pdf`, with
`Cache-Control: private, no-store` and `X-Content-Type-Options: nosniff`.
The UUID filename avoids putting untrusted metadata into response headers.
Files stream in 64 KiB chunks rather than being loaded entirely into memory.
Unauthorized credentials return 401; foreign/absent courses, missing documents,
missing/inaccessible files or invalid storage paths return 404. Invalid UUIDs
return 422. Responses do not expose stored filesystem paths.

For ingestion integration, `Document.file_path` should be storage-root-relative:
`uploads/{course_id}/{stored_filename}.pdf`. Local absolute paths returned by
`StorageService.save_upload` are also accepted when inside that exact course's
upload directory. Relative paths are preferred for moving deployments. The
metadata path may not select another course, a lesson asset or an external file.

This route serves existing records/files only; it does not implement upload
validation, PDF parsing or extraction. PDF content validity belongs to ingestion.
The storage filesystem must remain application-controlled: path checks do not
protect against hostile concurrent filesystem replacement. Read failures after
streaming begins cannot be converted into a new HTTP error response.

Run all backend tests (using disposable databases and files):

```powershell
.\.venv\Scripts\python.exe -m pytest Backend/tests -q -p no:cacheprovider -rs
```
